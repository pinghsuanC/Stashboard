# Stashboard

A developer knowledge hub for snippets, commands, prompts, notes, files, images, links and custom types.

**Live:** [stashboard-kohl.vercel.app](https://stashboard-kohl.vercel.app/)

## Features

- Items of seven system types, grouped into collections, with favourites, pinning and tags
- Command palette search (Cmd+K / Ctrl+K) across items and collections
- Code and Markdown editors, with file and image uploads stored privately in R2
- Email and password or GitHub sign-in, with email verification, password reset and rate limiting
- Free and Pro plans, with Stripe Checkout and plan limits enforced on the server

| Testing | Vitest |
| Hosting and CI | Vercel, GitHub Actions |

## Future Plans

Deferred work, to pick up in the polishing phase.

- **Attachments for every item type.** Let any item (a snippet, a note, ...) carry its own uploaded files, owned by one item, never shared. An `Attachment` table (`userId`, `itemId`, `key`, `name`, `size`, `mimeType`, cascading with its item) replaces the `Item.file*` columns; the storage service is reused as is. Open questions: do the File and Image types stay (as items with a required attachment)? Max attachments per item, and 5 MB per file or per item? Which file types attachments allow? Do it early, before production holds many uploads, so the migration moves little data.
- **Delete a user's R2 files with their account.** Deleting an account cascades their items in the database but leaves their uploads in R2. Delete everything under the `users/{userId}/` prefix (after the database delete succeeds), so the bucket holds no orphans.
- **Mitigate ignored audit warnings.** CI's dependency audit allowlists reviewed advisories in `audit-ci.jsonc` (braces via the shadcn CLI, deepmerge-ts and mysql2 via the Prisma CLI). Two gaps remain: a fix landing goes unnoticed until someone reads the unused-entry warning, and a reviewed package reaching the app another way is still accepted. Add a `.github/dependabot.yml` (npm and GitHub Actions, weekly, skipping Prisma 8) so fixes arrive as PRs, and scope each entry to its dependency path (e.g. `GHSA-vfj7-8cjw-p6xm|shadcn>fast-glob>micromatch>braces`) so a new path fails CI.
- **Rework the user session and its caching.** `getUserSession()` loads everything at once (profile, types, counts, pinned items, collections, and up to 50 search items), and every create, edit or delete reloads all of it through `resetProfile()`, even when only one slice changed. The search items also ride along on every full page load, used or not. Options to weigh: refresh only the slice that changed, or update it locally with the session setters (they exist but no save uses them yet); load the search items when the palette first opens instead of with the session; and cache per-user reads across requests (Next's `"use cache"` with tags, invalidated by the actions) without ever sharing one user's data with another.
- **Search past the preloaded items.** The search palette searches the session's `searchItems` in the browser, and `getSearchItems()` loads up to `SEARCH_ITEM_LIMIT` (50) of them, newest first. The cap is kept small so the session stays light, which means anything older than the newest 50 can't be found. When a search finds nothing locally, fall back to a server search: a debounced, rate-limited request to a user-scoped route or action that matches the same fields (title, type, description, file name, tags) in the database and returns item summaries, shown in the palette as they arrive. Open questions: whether to also query the server when there are a few local matches but the cap was hit, and whether Postgres full-text search or `ILIKE` on indexed columns is enough.
- **Paginate each collection section on its own.** `/collections/[slug]` loads one page of the collection's items (`ITEMS_PER_PAGE`, newest by `updatedAt`) and splits it into Items, Files and Images in memory, so a page's mix of types varies and each section shows only part of its items. Instead, run one query per section (filtered by type, each with its own `skip`/`take` and count) and give each section its own page links and URL parameter (e.g. `?items=2&files=1&images=3`), with section totals from the counts rather than the page. The section headers lost their `(n)` counts when pagination landed, because a page's count is only part of the section; each section's own count query restores them.
- **Count collection cards in the database.** `collectionCardSelect` (`src/lib/db/collections.ts`) fetches one join row, with its item's type, for every item in every collection, then counts and ranks the types in JS. `getSessionCollections()` runs it on every full page load inside `getUserSession()`, so the rows grow with total item-to-collection links. Use `_count` for the item count and one grouped query (`collectionId`, `typeId`, `count(*)` over `CollectionItem` joined to `Item`, scoped to the user) for the ranked types.
- **Share the editors' copy feedback.** `CodeEditor` and `MarkdownEditor` each declare `COPIED_ICON_MS` and their own copied-icon timer and copy handler. Move the constant to `constants/ui.ts` and extract a `useCopyFeedback(value)` hook returning `{ copied, copy }` in `components/items/` (not `src/hooks/`, which is shadcn's).
- **Move tuning values into constants.** `MAX_PAGE_LINKS` (`lib/helpers/pagination.ts`), `FIELD_MATCH_WEIGHT` (`lib/search/search.ts`) and the editors' padding are declared inline. `pageLinks()` also hard-codes thresholds (4, 5, 3) derived from 7, so changing `MAX_PAGE_LINKS` alone breaks its layout: derive them, with tests first.
- **Split the large item components.** `ItemDrawer` (~330 lines) into `ItemDrawerActions`, `ItemDrawerBody`, `ImagePreview` and `ItemMeta`, leaving the sheet shell and edit toggle; `ItemCreateDialog` (~230 lines) into an `ItemTypePicker` and a `useCreateItem` hook for the submit, upload and toast flow.
- **Fix sorting for items and collections.** Every list sorts by `updatedAt`, which does two jobs: "last edited" for the newest-first lists, and the order of `/favorites`, `/pinned` and the sidebar's Favorites. The star and pin toggles pull them apart. An item's star or pin writes `updatedAt` back unchanged, so the item doesn't jump pages behind the drawer. The cost: a read and a write in a transaction, an edit saved in between gets the older time back, and a newly starred or pinned item lands mid-list. A collection's star does move `updatedAt`, so it can reach the sidebar's 10 favourites, but it also reorders `/collections` and the dashboard cards. Fix: nullable `favoritedAt` on `Item` and `Collection` and `pinnedAt` on `Item`, set when the flag turns on and cleared when it turns off (in the same write), backfilled from `updatedAt`. Sort the favourite and pinned lists on them (then `id`), then pick one rule for both models on whether a toggle moves `updatedAt`, and simplify `setItemFlag` / `setCollectionFavorite` to match. Replace the `[userId, isFavorite]` / `[userId, isPinned]` indexes with `[userId, favoritedAt]` / `[userId, pinnedAt]` if the queries use them.
- **Add Paddle as a billing vendor.** Paddle (Paddle Billing, not Classic) is a merchant of record: it resells the plan to the customer and handles sales tax, VAT, refunds and chargebacks, for about 5% + 50¢ against Stripe's ~3.6%. Add it as an adapter in `services/billing/` behind the same interface as Stripe, chosen by `BILLING_PROVIDER` for new checkouts only, with webhooks at `/api/billing/paddle/webhook` (`Paddle-Signature`). It tests the interface: checkout is an overlay on the page (Paddle.js) rather than a redirect, so `createCheckout` must return either a redirect URL or overlay data. Sandbox only (`sandbox-vendors.paddle.com`); going live needs Paddle's business review.
- **Add more payment methods.** Each as an adapter in `services/billing/` behind the Stripe interface: ACH pay-by-bank through Stripe (`us_bank_account`), PayPal Subscriptions, and Authorize.net (Accept Hosted + ARB).
- **Add Item button on each type page.** `/items/[type]` has no way to add an item of that type; the only entry is the top bar's New Item, whose dialog opens on the first type. Add a button in the page header that opens the same `ItemCreateDialog` with that type picked. The dialog owns its trigger and state today (`TopBar` renders it, `pickedType` starts null), so it needs a way to open from elsewhere with a type: a provider like `UpgradePromptProvider` with an `openCreate(typeName)`, or an `initialType` prop. Only for `CREATABLE_ITEM_TYPE_NAMES`; a Pro-only type for a Free user still opens the upgrade dialog, as picking it in the dialog does.
- **Show cancelled subscriptions.** A Pro user who cancels in the Stripe portal keeps Pro until `periodEnd`, but nothing records the cancel: `BillingStatus` has no "cancels at period end" flag, so `/billings` can only say "Current period ends", never "Renews on" or "Cancelled, ends on". Handle `customer.subscription.updated` / `.deleted` in the webhook (signature-checked like the checkout events), store the cancel on the period row, carry it in `billing`, and word the plan card from it.
- **Switch plans (monthly ↔ yearly).** There's no plan switching for now: the Customer Portal offers cancel and payment updates only. When added, the stored period keeps the old interval until it ends, and a monthly-to-yearly switch resets the billing date, so the switch must also end the current period row and record the new one.
- **Make payment configurable instead of hard-coded.** Today the Pro plan's prices come from `STRIPE_PRICE_ID_*` env vars (a change needs a redeploy), the plans offered are fixed in code (monthly and yearly), and `BILLING_VENDOR` picks the vendor. Move these to configuration: which products and prices are offered (with their order and labels), and which payment vendors are enabled, editable from an admin page without a deploy. A first step is Stripe lookup keys (`stashboard_pro_monthly` / `stashboard_pro_yearly`, already on the sandbox prices), which remove stored price ids without a table. Open questions: a config table versus reading Stripe's catalog directly, and the admin role the page needs.
- **Disclose AI data use and redact secrets.** Suggest Tags sends an item's title and first 2,000 characters of content to OpenAI, and users store commands and `.env` snippets. There's no privacy page yet: add one that says Pro AI features send item text to OpenAI. Before each call, also replace strings shaped like secrets (`sk-…`, `AKIA…`, `ghp_…`, `-----BEGIN … KEY-----`) with `[REDACTED]`, in `lib/ai/` so every AI feature gets it, with tests first.
- **Make switching AI models easy to configure.** The model is fixed per feature in `AI_MODELS` (`src/lib/constants/ai.ts`), and `services/ai/openai.ts` only talks to OpenAI, so a new model needs a deploy and a new provider needs that service rewritten. Put the service behind a vendor-neutral adapter, as `BillingAdapter` does for billing, so OpenAI and Gemini are interchangeable, and choose the provider and model per feature from configuration. Keep the choice on the server: the client never sends a model. Providers differ in more than a name, so each adapter must own its quirks (OpenAI's `json_object` mode needs the word JSON in `input`), its JSON mode and its error mapping, and any reasoning effort setting must be optional. Compare data terms before adding one: Gemini's free tier may use content to improve products, which rules it out for users' item content. Open questions: env vars versus an admin page, and how to catch a retired model id, since OpenAI retires models within a year or two.
- **Share repeated UI.** `ItemDeleteDialog` and `CollectionDeleteDialog` are ~80% the same: one `ConfirmDeleteDialog` in `components/shared/`. The image grid, file list and item grid markup is repeated in `/items/[type]` and `/collections/[slug]`: `ImageGrid`, `FileList` and `ItemGrid` in `components/items/`. `CollectionDialog` hand-writes the label, error and `aria-describedby` wiring that `ItemFormFields`' `Field` helper already does: move `Field` to `components/shared/` and use it in both.
- **Link GitHub and password sign-in on the same email.** Today a GitHub sign-in whose email already has a password account is refused (`OAuthAccountNotLinked`, "Sign in the way you did before"), and registering an email a GitHub account already holds only sends the owner a notice. Let one user use both: link GitHub to the existing user when GitHub reports that email as verified and the password account's email is verified too (never Auth.js's `allowDangerousEmailAccountLinking` as is, which links on any matching email), and let a GitHub-only user add a password from Settings (`hasPassword` hides that section today) or through the reset-password email, never through register, which must still answer a taken email like a new one. Open questions: link silently or ask the signed-in user to confirm, and whether Settings should list and unlink connected sign-in methods.
